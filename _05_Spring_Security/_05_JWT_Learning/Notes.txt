Public-Private Key Cryptography :
    1. It is a Security Mechanism
    2. There are 2 keys generated in it
        1. Public Key :
            We can distribute Public Key
            Encrypted Data of Public key will be Decrypted by my own Private Key
        2. Private Key :
            We can't distribute Public Key (JWT works on this concept)

Stateless and Stateful :
    1. Stateless : It's state can't be stored in DB/File (JWT uses this)
    2. Stateful : It's state can be stored in DB/File

JWT (JSON Web Token) :
    1. JWT is Stateless
    2. Stateless means our server doesn't need to store all the information about user that are logged in currently like we don't need to manage dedicated authentication server and db that holds the data of all sessions at backend.
    3. Because, JWT is capable enough for holding all information needed to make sure the user that is logged in, is actually a valid user. So don't need to maintain DB separately for this.
    4. Scalable in Distributed System :
        4.1 With _csrf (Hard to Scale) :
            If there are 10 servers
            Every server needs to store session data
            And needs one shared session storage like Redis/DB
        4.2 With JWT (Easy to Scale):
            Token is stored on the client side
            Any server can verify the token and accept the request
            No shared session storage is needed
    5. Cross Domain Authentication :
        Cross-domain authentication means when a user logs in on one domain, but the authentication also works on another domain or subdomain.
        Example:
            Frontend: https://app.com
            Backend API: https://api.com
            The user logs in through app.com, but the requests are sent to api.com.
            If authentication works across both domains, it is called cross-domain authentication.
        Problem with Session-Based Authentication
                Session cookies like JSESSIONID are usually limited to the same domain.
                Sharing session cookies across different domains is difficult.
                CSRF protection also becomes more complex.
            So, cross-domain authentication is harder with session-based security.
        JWT Makes Cross-Domain Authentication Easy
            JWT tokens are stored on the client side.
            The client sends the token with every request in the header:
                Authorization: Bearer <token>
            Any server or domain can verify the token without needing shared session storage.
    6. Ideal for Decentralised systems and microservices :
        JWT is commonly used in microservices because each service can verify the token independently without relying on a central session store.
    7. Highly Secure :
        JWT is secure only when implemented correctly:
            Use HTTPS
            Use strong signing algorithms
            Keep token expiry short
            Store tokens safely (avoid localStorage for sensitive apps)

Understanding JWT :
    1. JWT is a compact, URL-safe of representing claims to be transferred between two parties
    2. JWT is often use to transmit non-sensitive data that doesn't require confidentially but still needs integrity and authenticity.
    3. It requires user identifiers, roles, permissions, and other claims necessary for making access control decisions.
    4. JWT is random collection of letters and numbers with 3 components by concatenating them with .
    5. First part is Header, Second part is Payload and Third part is Signature
    6. Structure of JWT :
        1. JWT Components
            Header = Type of Hashing Algorithm we will use for one way Hashing in Signature
            Payload = It is a non-sensitive data that we send for JWT Token creation. And not send sensitive data like password
            Signature = It is a Hashed (hashed according to algorithm we used in Header) version of [encodedHeader, encodedPayload, SecretKey]
                        Secret Key in JWT : A secret key is a private string used to sign the JWT token. It ensures that token is not modified and trusted by the server
                                            The secret key is stored securely on the server and is never shared with the client.
                                            It must be kept completely private, because anyone with the secret key can generate fake valid tokens.

            Header : {
                       "alg": "HS256",
                       "typ": "JWT"
                     }
            Payload : {
                        "userId": 101,
                        "name": "Shikhil",
                        "role": "USER",
                        "iat": 1700000000,  // Issued At
                        "exp": 1700003600   // Expiry of Token
                      }
            Signature : Base64URLSafe(
                            HMACSHA256(<header>,<payload>,<secret key>)
                        )

        2. Base64URLSafe Encoding of Header and Payload
            encodedHeader (Base64URLSafe Encoded) : eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9 (It determines the algorithm we are using)
            encodedPayload (Base64URLSafe Encoded) : eyJzdWIiOiJzaGlraGlscmFuZSIsInJvbGUiOiJVU0VSIiwiaWF0IjoxNzAwMDAwMDAwLCJleHAiOjE3MDAwMDM2MDB9 (Determines the data)

        3. Signature creation :
            Signature is used to determine there should not be any manipulation
            Signature = Encoding(Hash(Header + Payload, SecretKey))
            here,
                Signature = Base64URLSafe(HMACSHA256(
                                                     encodedHeader + "." + encodedPayload,
                                                     SecretKey
                                                    )
                                         )
                So:
                    Base64URLSafe = Base64URLSafe ek encoding method hai jo data ko JWT me URL-safe format me convert karta hai.
                    HMACSHA256 = Algorithm use to generate signature
                    Header + Payload = data.
                    Secret key is used to generate a hashed signature.
                    Signature proves token is not changed
                    
        4. JWT as output :
            JWT = encodedHeader.encodedPayload.Signature
                                                  |
                                                  V
                  Base64URLSafe(Hash(encodedHeader + encodedPayload, SecretKey))
            JWT Token = eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJzaGlraGlscmFuZSIsInJvbGUiOiJVU0VSIiwiaWF0IjoxNzAwMDAwMDAwLCJleHAiOjE3MDAwMDM2MDB9.W5XyUuQ0G0xH9Gm1gDqkOe6n4oKzH8YzR2xPpQ0sR9U

            If someone modifies the payload, the signature verification will fail, so the server will not accept the JWT.
            NOTE : An attacker cannot generate a valid new signature without knowing the secret key.

Authentication vs Authorization :
    | Term           | Meaning                 |
    | -------------- | ----------------------- |
    | Authentication | Verify user identity    |
    | Authorization  | Verify user permissions |

JWT Token vs Sessions :
    Sessions :
        Server user ka data store karta hai
        Client ke paas sirf JSESSIONID cookie hoti hai
        Stateful hota hai
        Multiple servers me scale karna hard hota hai (Redis/DB chahiye)
    JWT Token :
        Token client ke paas hota hai
        Server session store nahi karta
        Stateless hota hai
        Easily scalable (har server token verify kar leta hai)
