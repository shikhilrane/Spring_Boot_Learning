Resilience4j :
    Definition :
        Resilience4j is a lightweight fault-tolerance library used in microservices to handle service failures gracefully.
         (Service failures ko handle karke application ko stable banata hai)
    Purpose :
        Helps services remain available and responsive even when dependent services fail.
         (Dependency service fail hone par bhi application ko chalne deta hai)

    Why Resilience4j ?
        - Prevents cascading failures.
           (Ek service fail hone par baaki services ko fail hone se bachata hai)
        - Improves system reliability.
           (Application ko zyada reliable banata hai)
        - Improves fault tolerance.
           (Failures ko handle karne ki capability badhata hai)
        - Integrates easily with Spring Boot.
           (Spring Boot ke saath easily kaam karta hai)

    Key Features :
        Spring Boot Integration :
           Provides annotations and configuration support.
            (Annotations aur configuration ke through easily use kar sakte hain)
           Common Annotations :
               @Retry
                (Automatic retry)
               @RateLimiter
                (Request limit control)
               @CircuitBreaker
                (Failure protection)

        1. Retry
           Automatically retries a failed operation.
            (Fail hui request ko dobara try karta hai)
           Example :
               Inventory Service
                     ↓
                  Failed
                     ↓
                  Retry
                     ↓
                  Success
           Use Case :
               Temporary network issue.
                (Temporary connection issue)

        2. Rate Limiter
           Limits the number of requests allowed in a given time period.
            (Fixed time me limited requests allow karta hai)
           Example :
               Limit = 100 Requests / Minute
               Request 101
                    ↓
                 Blocked
           Use Case :
               Protecting services from excessive traffic.
                (Bahut zyada traffic se service ko bachata hai)

        3. Circuit Breaker
           Stops calling a failing service after a threshold is reached.
            (Service baar baar fail ho rahi ho to usko call karna temporarily band kar deta hai)
           Example :
               Order Service
                    ↓
               Inventory Service
                    ↓
                  Fail
                    ↓
                  Fail
                    ↓
                  Fail
                    ↓
               Circuit Opens
                    ↓
               Further Calls Blocked
           Benefit :
               Prevents wasting resources on continuously failing services.
                (Fail ho rahi service par resources waste nahi karta)

    Typical Microservice Flow :
        Order Service
              ↓
        Inventory Service
              ↓
        Service Failure
              ↓
        Resilience4j
              ↓
        Retry / Circuit Breaker / Rate Limiter
              ↓
        Controlled Response

    Summary :
        Resilience4j
            → Makes microservices more reliable and fault tolerant.
              (Microservices ko zyada stable aur reliable banata hai)
        1. Retry
            → Re-attempt failed requests.
              (Failed request ko dobara try karta hai)
        2. Rate Limiter
            → Controls request rate.
              (Request count control karta hai)
        3. Circuit Breaker
            → Stops repeated calls to failing services.
              (Failing service ko repeatedly call karne se rokta hai)

1. Retry :
    Retry is a Resilience4j feature that automatically retries a failed service call a fixed number of times before giving up.
     (Failed service call ko fixed number of times automatically dobara try karta hai)
    Used when failures are temporary and the service may become available after a short delay.
     (Temporary failures ko recover karne ke liye use hota hai)
    Annotation :
        @Retry(
            name = "inventoryRetry",
            fallbackMethod = "fallBackMethodReduceOrder"
        )
        here,
            name = "inventoryRetry"
                    → Name of the retry configuration.
                      (Retry configuration ko identify karne ke liye)
            fallbackMethod = "fallBackMethodReduceOrder"
                             → Method executed if all retry attempts fail.
                               (Saare retries fail hone ke baad execute hone wala method)
    Configuration :
        resilience4j:
          retry:
            configs:
              default:
                maxRetryAttempts: 3
                waitDuration: 5s
        here,
            maxRetryAttempts : 3
                               → Maximum number of retry attempts.
                               (Maximum 3 baar retry karega)
            waitDuration : 5s
                           → Time gap between retry attempts.
                           (Har retry ke beech 5 second wait karega)
    Flow :
        Service Call
             ↓
        Request Failed
             ↓
        Retry Attempt 1
             ↓
        Retry Attempt 2
             ↓
        Retry Attempt 3
             ↓
        Success
             OR
        Fallback Method
            (Success mil jaye to request complete ho jayegi, warna fallback method execute hoga)

2. Rate Limiter :
    Rate Limiter is a Resilience4j feature that controls the rate of requests by limiting the number of calls allowed during a specific time period.
     (Defined time period ke andar limited requests hi allow karta hai)
    Used to protect services from excessive traffic and prevent system overload.
     (Zyada traffic aur overload se service ko bachane ke liye use hota hai)
    Annotation :
        @RateLimiter(
            name = "inventoryRateLimiter",
            fallbackMethod = "fallBackMethodReduceOrder"
        )
        here,
            name = "inventoryRateLimiter"
                    → Name of the rate limiter configuration.
                      (Rate limiter configuration ko identify karne ke liye)
            fallbackMethod = "fallBackMethodReduceOrder"
                             → Method executed when request limit is exceeded.
                               (Request limit cross hone par execute hone wala method)
    Configuration :
        resilience4j:
          ratelimiter:
            configs:
              default:
                limitForPeriod: 1
                limitRefreshPeriod: 5s
                timeoutDuration: 1s
        here,
            limitForPeriod : 1
                             → Maximum requests allowed in one refresh period.
                               (Ek refresh period me sirf 1 request allow hogi)
            limitRefreshPeriod : 5s
                                 → Time after which request count is reset.
                                   (Har 5 second baad request count reset hoga)
            timeoutDuration : 1s
                              → Time to wait for permission before request fails.
                                (Request fail hone se pehle 1 second wait karega)
    Flow :
        Request 1
             ↓
          Allowed
             ↓
        Request 2
             ↓
        Limit Exceeded
             ↓
        Wait for Permission
             ↓
        Timeout Reached
             ↓
        Fallback Method

            (Limit ke andar request allow hogi, warna fallback method execute hoga)

3. Circuit Breaker :
    Circuit Breaker is a Resilience4j pattern that prevents an application from repeatedly calling a service that is already failing.
     (Jo service lagatar fail ho rahi ho usko bar bar call karna temporarily stop kar deta hai)
    Used to avoid wasting resources and improve system stability when a dependent service is unavailable.
     (Resources bachane aur system ko stable rakhne ke liye use hota hai)

    Annotation :
        @CircuitBreaker(
            name = "inventoryFeignClient",
            fallbackMethod = "fallBackMethodReduceOrder"
        )

        here,

            name = "inventoryFeignClient"
                    → Name of the circuit breaker configuration.
                      (Circuit breaker configuration ko identify karne ke liye)

            fallbackMethod = "fallBackMethodReduceOrder"
                             → Method executed when service fails or circuit is open.
                               (Service fail hone ya circuit open hone par execute hone wala method)

    Configuration :
        Circuit Breaker Health Monitoring :
            management:
              health:
                circuitbreakers:
                  enabled: true
              endpoints:
                web:
                  exposure:
                    include: "*"
              endpoint:
                health:
                  show-details: always
            here,
                management
                              → Root configuration for Spring Boot Actuator.
                                (Actuator related configurations yaha likhte hain)
                    health:
                        circuitbreakers:
                            enabled: true
                            → Enables Circuit Breaker health monitoring.
                              (Circuit Breaker ka health status enable karta hai)
                    endpoints:
                        web:
                            exposure:
                                include: "*"
                                → Exposes all Actuator endpoints over HTTP.
                                  (Saare Actuator endpoints access karne deta hai)
                    endpoint:
                        health:
                            show-details: always
                            → Always shows detailed health information.
                              (Health endpoint par complete details dikhata hai)
                Use Case :
                    URL :
                        http://localhost:9020/orders/actuator OR http://localhost:8080/api/v1/orders/actuator
                    Response :
                        {
                          "status": "UP",
                          "components": {
                            "circuitBreakers": {
                              "status": "UP"
                            }
                          }
                        }
                        → Used to monitor Circuit Breaker state and application health.
                          (Application aur Circuit Breaker ki health check karne ke liye)
        Circuit Breaker Configuration :
            resilience4j:
              circuitbreaker:
                instances:
                    registerHealthIndicator: true
                    slidingWindowSize: 10
                    slidingWindowType: COUNT_BASED
                    minimumNumberOfCalls: 10
                    failureRateThreshold: 50
                    waitDurationInOpenState: 1s
                    permittedNumberOfCallsInHalfOpenState: 3
                    eventConsumerBufferSize: 10
                    automaticTransitionFromOpenToHalfOpenEnabled: true
            here,
                registerHealthIndicator : true
                                          → Exposes Circuit Breaker health information through Actuator.
                                            (Circuit Breaker ka health status monitor karne ke liye)
                slidingWindowSize : 10
                                    → Uses last 10 requests to calculate failure rate.
                                      (Aakhri 10 requests ke basis par failure rate calculate hota hai)
                slidingWindowType : COUNT_BASED
                                    → Uses request count instead of time duration.
                                      (Time nahi, request count ke basis par calculation hoti hai)
                minimumNumberOfCalls : 10
                                       → At least 10 requests are required before evaluating failure rate.
                                         (Failure rate calculate karne se pehle minimum 10 requests chahiye)
                failureRateThreshold : 50
                                       → Circuit opens if 50% or more requests fail.
                                         (Agar 10 me se 5 ya usse zyada requests fail ho jaye to circuit OPEN ho jata hai)
                waitDurationInOpenState : 1s
                                          → Circuit remains OPEN for 1 second before moving to HALF_OPEN.
                                            (OPEN state me 1 second tak rahega)
                permittedNumberOfCallsInHalfOpenState : 3
                                                         → Allows 3 test requests in HALF_OPEN state.
                                                           (Recovery check karne ke liye 3 requests allow hoti hain)
                eventConsumerBufferSize : 10
                                          → Stores last 10 circuit breaker events.
                                            (Last 10 events memory me store karta hai)
                automaticTransitionFromOpenToHalfOpenEnabled : true
                                                                → Automatically moves from OPEN to HALF_OPEN state.
                                                                  (Manual intervention ke bina recovery testing start hoti hai)

    States :
        CLOSED
            → Requests are allowed normally.
              (Service healthy hai)
        OPEN
            → Requests are blocked and fallback method is called.
              (Service unhealthy hai)
        HALF-OPEN
            → Limited requests are allowed for testing recovery.
              (Service recover hui hai ya nahi check karta hai)

    Flow :
            Service Running
                  ↓
                CLOSED
                  ↓
            Too Many Failures
                  ↓
                 OPEN
                  ↓
             Wait 10 Seconds
                  ↓
              HALF-OPEN
                  ↓
        Success      Failure
           ↓            ↓
        CLOSED       OPEN

            (Service recover ho jaye to CLOSED, warna fir se OPEN state me chala jata hai)

Code :
    Add Resilience4J Dependency
            <dependency>
                <groupId>org.springframework.cloud</groupId>
                <artifactId>spring-cloud-starter-circuitbreaker-resilience4j</artifactId>
            </dependency>
    1. Retry :
           In order-service, make createOrder() resilient because it calls reduceStocks() through OpenFeignClient.
           Create configuration in application.yml file for @Retry
           So, Apply @Retry(name = "inventoryRetry", fallbackMethod = "createOrderFallback") annotation to it
           name = name of retry configuration and fallbackMethod = if it fails to connect then this method will execute
    2. Rate Limiter :
           In order-service, make createOrder() resilient against excessive requests as this method is calling reduceStocks from OpenFeignClient
           Create configuration in application.yml file for @RateLimiter
           So, Apply @RateLimiter(name = "inventoryRateLimiter", fallbackMethod = "createOrderFallback")
           name = name of rate limiter configuration and fallbackMethod = if it fails to connect then this method will execute
    3. Circuit Breaker :
           In order-service, make createOrder() resilient against repeated service failures.
           Create configuration in application.yml file for @CircuitBreaker
           NOTE : Remove @Retry and @RateLimiter as @CircuitBreaker does not work along with it @Retry
           So, Apply @CircuitBreaker(name = "inventoryCircuitBreaker", fallbackMethod = "createOrderFallback")
           name = name of circuit breaker configuration and fallbackMethod = if it fails to connect then this method will execute
